# Review Criteria: Название встречи рядом с записью в предстоящих событиях

## Проверяемые сценарии (из спецификации #9)

### 1. Основной сценарий
**Условие:** Гость записан на слот, владелец открывает «Предстоящие события»
**Ожидаемое поведение:**
- Карточка брони содержит строку названия встречи (например, «Созвон на 30 минут»)
- Название стоит между email и строкой «Слот: YYYY-MM-DD-HH:MM»
- Название читается из поля `eventTypeName` ответа API (через сгенерированный SDK)
- Сортировка списка и состав карточек без изменений

**Что проверять:**
- HTTP-ответ `GET /api/bookings` содержит `eventTypeName` = `title` типа
- Фронт отрисовывает строку названия между email и «Слот»
- E2E-проход: существующий флоу записи, название видно

### 2. Негативный сценарий
**Условие:** Тип встречи не найден в хранилище (`eventTypeId` отсутствует или невалиден)
**Ожидаемое поведение:**
- API возвращает `200` с `eventTypeName: null`
- Ответ не падает, карточка сохраняет структуру
- Строка названия **не рендерится** (fallback), остальные строки без изменений
- Пустой список всё ещё показывает «Предстоящих событий нет.»

**Что проверять:**
- Бронь с несуществующим `eventTypeId` в хранилище → `200` + `eventTypeName: null`
- Фронт: карточка без строки названия, другие строки прежние
- E2E: сценарий не ломает страницу

### 3. Соседний сценарий
**Условие:** Пустой список и обычное бронирование без изменений
**Ожидаемое поведение:**
- `GET /api bookings` при пустом списке → `200 []`
- `POST /api bookings` по-прежнему работает (создание новой брони)
- Страница «Предстоящие события» показывает «Предстоящих событий нет.»
- Обычное бронирование на слот работает как раньше (без названия)

**Что проверять:**
- Пустой список не ломает страницу
- Форма записи гостя не страдает от изменения контракта
- E2E: флоу бронирования зелёный без изменений текста
